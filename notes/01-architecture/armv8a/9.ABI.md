# 9.ABI
## 通用目的寄存器作为参数
出于函数调用的目的，通用寄存器分为四组：
Argument registers (X0-X7) : 参数寄存器 x0-x7
这些寄存器用于将参数传递给函数并返回结果。它们可以用作临时寄存器或调用者保
存的寄存器变量（译注：传入参数）
，可以在函数内保存中间值，或者函数调用之间传
递参数。与 AArch32 相比，8 个寄存器可用于参数传递，这样减少了因参数过多放入
堆栈的需要。
Caller-saved temporary registers (X9-X15)（调用者）
如果调用者需要在调用另一个函数时保留一些寄存器中的任何值，则调用者必须将受
影响的寄存器保存在自己的堆栈帧中。也可以修改子例程，（译注：使用 x9-x15 实现
相同功能，）而不需要在返回调用函数时保存值到堆栈和从堆栈中恢复它们。
Callee-saved registers (X19-X29)（被调用）
这些寄存器保存在被调用者内部。只要在返回前保存并恢复，就可以在被调用的子程
序中修改。
Registers with a special purpose (X8, X16-X18, X29, X30) 特殊目的寄存器
• X8 是间接结果寄存器。这用于传递间接结果的地址位置，例如，函数返回大型结构的位
置。（译注：不只是返回，函数内部有大的结构体也会使用）
• X16 和 X17 分别是 IP0 和 IP1，intra-procedure-call 临时寄存器
这些可以通过 veneers 或者类似代码使用，或者作为子程序调用之间的中间值的临时寄存器。
它们可以被函数破坏。veneers 代码是链接器自动插入的一小段代码，例如当分支（跳转）目
标超出分支指令（支持的）范围时。
• X18 是平台寄存器，保留供平台 ABI 使用。这是平台上的一个附加临时寄存器，没有为其
分配特殊含义。
• X29 是 Frame Pointer 寄存器（FP）
• X30 是链接寄存器 (LR)。

## 内核侧 ABI 总览

上面是 AAPCS64 对**函数调用**的寄存器约定。但一个完整的用户态 ABI 远不止函数调用，它还包括：用户态如何陷入内核、内核如何把寄存器现场交还给调试器、信号处理函数如何被"调用"、线程本地存储放在哪个寄存器、以及用户态如何探测 CPU 能力。这些约定在 Linux 里都有对应的实现代码，本节逐一展开。

| ABI 面 | 用户态可见形式 | 内核实现 |
| :-- | :-- | :-- |
| 系统调用 | `svc #0`，x8 传调用号，x0-x5 传参 | `arch/arm64/kernel/syscall.c`、`arch/arm64/kernel/sys.c` |
| 寄存器现场 | `ptrace(PTRACE_GETREGSET)`、core dump | `arch/arm64/kernel/ptrace.c` 的 regsets |
| 信号投递 | handler 收到 x0/x1/x2，栈上是 `rt_sigframe` | `arch/arm64/kernel/signal.c` |
| TLS | `tpidr_el0`（`mrs x0, tpidr_el0`） | `arch/arm64/kernel/process.c` 的 `tls_thread_switch` |
| 能力探测 | `getauxval(AT_HWCAP)`、`/proc/cpuinfo` | `arch/arm64/kernel/cpufeature.c` 的 `arm64_elf_hwcaps[]` |
| 指针认证 | PACIASP/AUTIASP、`prctl(PR_PAC_*)` | `arch/arm64/include/asm/pointer_auth.h` |
| 向量扩展 | SVE/SME 指令、`NT_ARM_SVE` | `arch/arm64/kernel/fpsimd.c` |

一个贯穿全篇的设计原则：**内核内部保存的寄存器布局，其前缀必须与用户态可见的布局完全一致**。这条约束被写成编译期断言，见 `arch/arm64/include/asm/ptrace.h:154` 的注释"struct user_pt_regs must form a prefix of struct pt_regs"。

## 系统调用入口与参数传递

### SVC 与异常向量

AAPCS64 规定 x0-x7 传参，但 Linux 系统调用 ABI 只用了 **x0-x5 六个参数寄存器**，x8 被征用为调用号，x6/x7 不参与传参。这是 Linux 自己的约定，不是 AAPCS64 的一部分。

用户态执行 `svc #0` 触发同步异常，ESR_EL1.EC = `ESR_ELx_EC_SVC64`。异常向量表第 3 组第 1 槽（`kernel_ventry 0, t, 64, sync`）接住它，经 `el0t_64_sync` stub 进入 `el0t_64_sync_handler()`（`arch/arm64/kernel/entry-common.c:749`），按 EC 分派到 `el0_svc()`：

```c
/* arch/arm64/kernel/entry-common.c:730 */
static void noinstr el0_svc(struct pt_regs *regs)
{
	arm64_syscall_enter_from_user_mode(regs);
	cortex_a76_erratum_1463225_svc_handler();
	fpsimd_syscall_enter();
	local_daif_restore(DAIF_PROCCTX);
	do_el0_svc(regs);
	arm64_syscall_exit_to_user_mode(regs);
	fpsimd_syscall_exit();
}
```

注意顺序：先做进入用户态→内核态的上下文记账（RCU/context tracking/lockdep），再处理 Cortex-A76 勘误，然后按 ABI 要求清理 SVE/SME 状态，**最后才放开中断**（`DAIF_PROCCTX` = 0）。系统调用主体是在开中断、可抢占的环境下跑的，这与中断处理程序截然不同。

### pt_regs：内核保存的寄存器视图

`kernel_entry` 宏把用户态 GPR 压到内核栈上，形成 `struct pt_regs`（`arch/arm64/include/asm/ptrace.h:156`）：

```c
struct pt_regs {
	union {
		struct user_pt_regs user_regs;
		struct {
			u64 regs[31];
			u64 sp;
			u64 pc;
			u64 pstate;
		};
	};
	u64 orig_x0;
	s32 syscallno;
	u32 pmr;

	u64 sdei_ttbr1;
	struct frame_record_meta stackframe;
};
```

前半部分与 UAPI 的 `struct user_pt_regs`（`arch/arm64/include/uapi/asm/ptrace.h:88`）逐字段重合：

```c
struct user_pt_regs {
	__u64		regs[31];
	__u64		sp;
	__u64		pc;
	__u64		pstate;
};
```

`regs[31]` 对应 x0-x30，**没有 x31**——因为 AArch64 的 x31 编码在大多数指令里是 SP 或 ZR，不是通用寄存器。SP 单独存一份。后半部分 `orig_x0`/`syscallno`/`pmr` 是内核私有的，不会暴露给用户态，这正是"前缀相同"设计的价值：ptrace 可以直接把 `user_regs` 整块拷出去，无需重排。

`static_assert(IS_ALIGNED(sizeof(struct pt_regs), 16))` 保证整个结构 16 字节对齐，满足 AAPCS64 的栈对齐要求。

### el0_svc_common 与调用号

`do_el0_svc()`（`arch/arm64/kernel/syscall.c:138`）只做一件事——把 x8 作为调用号传下去：

```c
void do_el0_svc(struct pt_regs *regs)
{
	el0_svc_common(regs, regs->regs[8], __NR_syscalls, sys_call_table);
}
```

`el0_svc_common()`（`arch/arm64/kernel/syscall.c:62`）是真正的调度中心：

```c
static void el0_svc_common(struct pt_regs *regs, int scno, int sc_nr,
			   const syscall_fn_t syscall_table[])
{
	unsigned long flags = read_thread_flags();

	regs->orig_x0 = regs->regs[0];
	regs->syscallno = scno;
	...
	if (unlikely(flags & _TIF_MTE_ASYNC_FAULT)) {
		syscall_set_return_value(current, regs, -ERESTARTNOINTR, 0);
		return;
	}

	if (has_syscall_work(flags)) {
		if (scno == NO_SYSCALL)
			syscall_set_return_value(current, regs, -ENOSYS, 0);
		scno = syscall_trace_enter(regs);
		if (scno == NO_SYSCALL)
			goto trace_exit;
	}

	invoke_syscall(regs, scno, sc_nr, syscall_table);
	...
trace_exit:
	syscall_trace_exit(regs);
}
```

几个 ABI 层面的关键点：

1. **`orig_x0` 备份**。x0 既是第一个参数又是返回值寄存器，一旦系统调用执行完就被覆盖。ptrace 的 `PTRACE_GET_SYSCALL_INFO`、audit、seccomp 都需要看到"原始的第一个参数"，所以进入时先存一份。`syscall_get_arguments()`（`arch/arm64/include/asm/syscall.h:80`）读的正是 `orig_x0` 而非 `regs[0]`。
2. **MTE 异步标签错误优先**。若 `_TIF_MTE_ASYNC_FAULT` 置位，系统调用根本不执行，直接返回 `-ERESTARTNOINTR`，让 `do_notify_resume()` 先发信号再重启调用。
3. **ptrace 跳过调用的约定**。tracer 把调用号设成 -1（`NO_SYSCALL`）表示"跳过"，但内核无法区分这与用户态真的调用 `syscall(-1)`，所以先把 x0 设成 `-ENOSYS` 兜底。这段注释在源码里占了十几行，是 ABI 兼容性的典型妥协。
4. **BTI 的 BTYPE 不清零**。源码注释明确说明：架构不保证 SVC 时 SPSR.BTYPE 为 0，内核**故意不动** `regs->pstate & PSR_BTYPE_MASK`。如果用户态自己把 PROT_BTI 页搞乱，返回时吃 SIGILL 是活该。

### sys_call_table 与 SYSCALL_DEFINE 包装

调用表在 `arch/arm64/kernel/sys.c:60` 用两次 include 同一个生成头文件的手法构造：

```c
#undef __SYSCALL
#define __SYSCALL(nr, sym)	asmlinkage long __arm64_##sym(const struct pt_regs *);
#include <asm/syscall_table_64.h>

#undef __SYSCALL
#define __SYSCALL(nr, sym)	[nr] = __arm64_##sym,

const syscall_fn_t sys_call_table[__NR_syscalls] = {
	[0 ... __NR_syscalls - 1] = __arm64_sys_ni_syscall,
#include <asm/syscall_table_64.h>
};
```

第一遍展开成函数声明，第二遍展开成数组初始化器。先用 GCC 的区间初始化器把**所有槽位**填成 `__arm64_sys_ni_syscall`（返回 -ENOSYS），再让生成的表覆盖有效槽位——这样任何未实现的调用号都自动落到"未实现"而不是空指针。

表里的函数签名统一是 `long (*)(const struct pt_regs *)`，而不是各自的原生参数列表。这层转换由 `arch/arm64/include/asm/syscall_wrapper.h` 的 `__SYSCALL_DEFINEx` 宏完成：

```c
#define SC_ARM64_REGS_TO_ARGS(x, ...)				\
	__MAP(x,__SC_ARGS					\
	      ,,regs->regs[0],,regs->regs[1],,regs->regs[2]	\
	      ,,regs->regs[3],,regs->regs[4],,regs->regs[5])

#define __SYSCALL_DEFINEx(x, name, ...)						\
	asmlinkage long __arm64_sys##name(const struct pt_regs *regs);		\
	static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__));		\
	static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__));	\
	asmlinkage long __arm64_sys##name(const struct pt_regs *regs)		\
	{									\
		return __se_sys##name(SC_ARM64_REGS_TO_ARGS(x,__VA_ARGS__));	\
	}									\
	static long __se_sys##name(__MAP(x,__SC_LONG,__VA_ARGS__))		\
	{									\
		long ret = __do_sys##name(__MAP(x,__SC_CAST,__VA_ARGS__));	\
		__MAP(x,__SC_TEST,__VA_ARGS__);					\
		__PROTECT(x, ret,__MAP(x,__SC_ARGS,__VA_ARGS__));		\
		return ret;							\
	}									\
	static inline long __do_sys##name(__MAP(x,__SC_DECL,__VA_ARGS__))
```

三层结构各有用途：

- `__arm64_sys_*`：ABI 入口，只认 pt_regs，负责从 x0-x5 取参。
- `__se_sys_*`：sign-extension 层，把所有参数先提升为 `long`，再 `__SC_CAST` 回目标类型。这是为了消除 32 位参数在高 32 位携带垃圾时的符号扩展问题（历史上曾导致内核越界访问）。`__PROTECT` 展开为 `asmlinkage_protect`（`include/linux/syscalls.h:238`），防止编译器把参数寄存器当作可复用的临时寄存器。
- `__do_sys_*`：开发者实际写函数体的地方，参数类型是干净的。

`invoke_syscall()`（`arch/arm64/kernel/syscall.c:38`）在查表前还做了两件事：

```c
	add_random_kstack_offset();

	if (likely(scno < sc_nr)) {
		syscall_fn_t syscall_fn;
		syscall_fn = syscall_table[array_index_nospec(scno, sc_nr)];
		ret = __invoke_syscall(regs, syscall_fn);
	} else {
		ret = do_ni_syscall(regs, scno);
	}

	syscall_set_return_value(current, regs, 0, ret);
```

`array_index_nospec()` 阻断 Spectre-v1 式的越界投机读表；`add_random_kstack_offset()` 每次系统调用随机化内核栈起始偏移，增加 ROP 难度。

### 返回值、orig_x0 与重启

返回值写回 x0，由 `syscall_set_return_value()`（`arch/arm64/include/asm/syscall.h:51`）统一处理：

```c
static inline void syscall_set_return_value(struct task_struct *task,
					    struct pt_regs *regs,
					    int error, long val)
{
	if (error)
		val = error;

	if (is_compat_thread(task_thread_info(task)))
		val = lower_32_bits(val);

	regs->regs[0] = val;
}
```

内核内部用 `-errno` 表示失败，用户态看到的也是负值（libc 再转成 `errno` + 返回 -1）。`syscall_rollback()` 把 x0 恢复成 `orig_x0`，用于信号导致的系统调用重启：

```c
static inline void syscall_rollback(struct task_struct *task,
				    struct pt_regs *regs)
{
	regs->regs[0] = regs->orig_x0;
}
```

重启时还需要把调用号改回 `__NR_restart_syscall`，见 `setup_restart_syscall()`（`arch/arm64/kernel/signal.c:1577`）：

```c
static void setup_restart_syscall(struct pt_regs *regs)
{
	if (is_compat_task())
		compat_setup_restart_syscall(regs);
	else
		regs->regs[8] = __NR_restart_syscall;
}
```

### 调用链

```
用户态 svc #0（x8=调用号, x0-x5=参数）
  → vectors: kernel_ventry 0, t, 64, sync
  → el0t_64_sync（kernel_entry 保存 GPR 到 pt_regs）
  → el0t_64_sync_handler()             [entry-common.c]
  → el0_svc()
      arm64_syscall_enter_from_user_mode()
      fpsimd_syscall_enter()           // 退出 streaming mode，清 SVE 高位
      local_daif_restore(DAIF_PROCCTX) // 开中断
  → do_el0_svc()                       [syscall.c]
  → el0_svc_common(regs, regs->regs[8], __NR_syscalls, sys_call_table)
      regs->orig_x0 = regs->regs[0]
      syscall_trace_enter()            // ptrace/seccomp/audit
  → invoke_syscall() → sys_call_table[scno]
  → __arm64_sys_xxx(regs) → __se_sys_xxx() → __do_sys_xxx()
  → syscall_set_return_value() → regs->regs[0]
  → syscall_trace_exit()
  → arm64_syscall_exit_to_user_mode() → fpsimd_syscall_exit()
  → ret_to_user → kernel_exit 0 → eret
```

## 信号帧布局

信号投递本质上是**内核替用户态构造一次函数调用**：设置好参数寄存器、栈指针、返回地址，然后 `eret` 回去。被"调用"的是信号处理函数，而"返回地址"指向一段会执行 `rt_sigreturn` 的 trampoline。

### rt_sigframe 与扩展上下文链

基础帧极简（`arch/arm64/kernel/signal.c:45`）：

```c
/*
 * Do a signal return; undo the signal stack. These are aligned to 128-bit.
 */
struct rt_sigframe {
	struct siginfo info;
	struct ucontext uc;
};
```

`uc.uc_mcontext` 里嵌着一个 `struct user_pt_regs` 的等价物（regs[31]/sp/pc/pstate/fault_address），后面跟一个 `__reserved[4096]` 字节数组。所有可选的扩展状态（FPSIMD、ESR、SVE、ZA、ZT、TPIDR2、FPMR、POE、GCS）都以 **magic+size 头 + 数据** 的记录形式串在这个保留区里，最后用一条 magic=0 的终止记录收尾。

布局由 `struct rt_sigframe_user_layout`（`arch/arm64/kernel/signal.c:50`）描述：

```c
struct rt_sigframe_user_layout {
	struct rt_sigframe __user *sigframe;
	struct frame_record __user *next_frame;

	unsigned long size;	/* size of allocated sigframe data */
	unsigned long limit;	/* largest allowed size */

	unsigned long fpsimd_offset;
	unsigned long esr_offset;
	unsigned long gcs_offset;
	unsigned long sve_offset;
	unsigned long tpidr2_offset;
	unsigned long za_offset;
	unsigned long zt_offset;
	unsigned long fpmr_offset;
	unsigned long poe_offset;
	unsigned long extra_offset;
	unsigned long end_offset;
};
```

每个 `_offset` 为 0 表示该记录不存在。这种"偏移表"设计让内核可以按当前任务实际用到的状态动态裁剪帧大小——一个从未碰过 SVE 的进程，信号帧里就不会有 SVE 记录。

`__reserved` 区放不下时，`__sigframe_alloc()`（`arch/arm64/kernel/signal.c:184`）会插入一条 `extra_context` 记录，把后续数据引到帧外的额外空间，上限 `SIGFRAME_MAXSZ`（256K）。源码注释特意强调这个上限 **"is not a guarantee and is NOT ABI"**——用户态不能依赖它。

### 帧布局计算

`setup_sigframe_layout()`（`arch/arm64/kernel/signal.c:1172`）按固定顺序分配各记录：

```c
	if (system_supports_fpsimd()) {
		err = sigframe_alloc(user, &user->fpsimd_offset,
				     sizeof(struct fpsimd_context));
		...
	}

	/* fault information, if valid */
	if (add_all || current->thread.fault_code) {
		err = sigframe_alloc(user, &user->esr_offset,
				     sizeof(struct esr_context));
		...
	}
	...
	if (system_supports_sve() || system_supports_sme()) {
		unsigned int vq = 0;

		if (add_all || current->thread.fp_type == FP_STATE_SVE ||
		    thread_sm_enabled(&current->thread)) {
			int vl = max(sve_max_vl(), sme_max_vl());

			if (!add_all)
				vl = thread_get_cur_vl(&current->thread);

			vq = sve_vq_from_vl(vl);
		}

		err = sigframe_alloc(user, &user->sve_offset,
				     SVE_SIG_CONTEXT_SIZE(vq));
		...
	}
```

`add_all` 参数用于 `sigaltstack` 尺寸计算与 `AT_MINSIGSTKSZ`：传 true 时按"最大可能状态"布局，保证用户态预留的备用栈一定够用。SVE 记录大小随向量长度（VL）变化，`vq = 0` 时只存头部不存向量数据。

`get_sigframe()`（`arch/arm64/kernel/signal.c:1404`）负责在用户栈上定位：

```c
	init_user_layout(user);
	err = setup_sigframe_layout(user, false);
	...
	sp = sp_top = sigsp(regs->sp, ksig);

	sp = round_down(sp - sizeof(struct frame_record), 16);
	user->next_frame = (struct frame_record __user *)sp;

	sp = round_down(sp, 16) - sigframe_size(user);
	user->sigframe = (struct rt_sigframe __user *)sp;

	if (!access_ok(user->sigframe, sp_top - sp))
		return -EFAULT;
```

先在栈顶放一个 `frame_record`（fp/lr 对），供栈回溯用；再往下放真正的 sigframe，全部 16 字节对齐。`sigsp()` 会考虑 `SA_ONSTACK` 与 sigaltstack。

### setup_return：把信号投递变成一次间接调用

`setup_return()`（`arch/arm64/kernel/signal.c:1475`）是 ABI 约定最密集的地方：

```c
	regs->regs[0] = usig;
	if (ksig->ka.sa.sa_flags & SA_SIGINFO) {
		regs->regs[1] = (unsigned long)&user->sigframe->info;
		regs->regs[2] = (unsigned long)&user->sigframe->uc;
	}
	regs->sp = (unsigned long)user->sigframe;
	regs->regs[29] = (unsigned long)&user->next_frame->fp;
	regs->regs[30] = (unsigned long)sigtramp;
	regs->pc = (unsigned long)ksig->ka.sa.sa_handler;
```

对照本文开头的 AAPCS64 约定：x0/x1/x2 是前三个参数（信号号、siginfo 指针、ucontext 指针），x29 是 FP，x30 是 LR。内核把 LR 设成 trampoline 地址，于是 handler 执行 `ret` 时就会跳到 trampoline，进而执行 `rt_sigreturn` 系统调用。trampoline 优先用 `SA_RESTORER` 指定的地址，否则用 vDSO 里的 `sigtramp` 符号。

紧接着是 BTI 处理：

```c
	if (system_supports_bti()) {
		regs->pstate &= ~PSR_BTYPE_MASK;
		regs->pstate |= PSR_BTYPE_C;
	}

	/* TCO (Tag Check Override) always cleared for signal handlers */
	regs->pstate &= ~PSR_TCO_BIT;

	/* Signal handlers are invoked with ZA and streaming mode disabled */
	if (system_supports_sme()) {
		task_smstop_sm(current);
		current->thread.svcr &= ~SVCR_ZA_MASK;
		write_sysreg_s(0, SYS_TPIDR2_EL0);
	}
```

`PSR_BTYPE_C` 模拟 `BLR <reg>` 的效果——因为信号投递在架构上就是一次间接调用。若 handler 落在 PROT_BTI 页但不是合法函数入口，用户态会吃 SIGILL。SME 的 ZA 与 streaming mode 则被强制关闭，这是 ABI 明确规定的：handler 不能继承调用者的 ZA 状态。

`setup_rt_frame()`（`arch/arm64/kernel/signal.c:1537`）把上述步骤串起来，并特别处理**失败点**：

```c
	fpsimd_save_and_flush_current_state();

	if (get_sigframe(&user, ksig, regs))
		return 1;

	save_reset_user_access_state(&ua_state);
	...
	err |= __save_altstack(&frame->uc.uc_stack, regs->sp);
	err |= setup_sigframe(&user, regs, set, &ua_state);
	if (ksig->ka.sa.sa_flags & SA_SIGINFO)
		err |= copy_siginfo_to_user(&frame->info, &ksig->info);

	if (err == 0)
		err = setup_return(regs, ksig, &user, usig);

	/*
	 * We must not fail if setup_return() succeeded - see comment at the
	 * beginning of setup_return().
	 */
```

一旦 `setup_return()` 改过 SP/PC，就不能再失败——否则嵌套 SIGSEGV 的 sigreturn 会恢复到"半个"状态。

### rt_sigreturn

返回路径由 `SYSCALL_DEFINE0(rt_sigreturn)`（`arch/arm64/kernel/signal.c:1126`）实现：

```c
	struct pt_regs *regs = current_pt_regs();
	...
	if (regs->sp & 15)
		goto badframe;

	frame = (struct rt_sigframe __user *)regs->sp;

	if (!access_ok(frame, sizeof (*frame)))
		goto badframe;

	if (restore_sigframe(regs, frame, &ua_state))
		goto badframe;
	...
	return regs->regs[0];

badframe:
	arm64_notify_segfault(regs->sp);
	return 0;
```

帧地址直接取自当前 SP（因为 handler 返回时 SP 恰好指回帧首），16 字节对齐是硬性检查。`restore_sigframe()` → `parse_user_sigframe()` 遍历 magic/size 链，逐条恢复 FPSIMD/SVE/ZA/ZT/PAC 等状态。任何校验失败都走 `arm64_notify_segfault()`，即 SIGSEGV。

文件末尾那一长串 `static_assert`（`arch/arm64/kernel/signal.c:1726` 起）把 `siginfo_t` 的每个字段偏移钉死：

```c
static_assert(sizeof(siginfo_t) == 128);
static_assert(__alignof__(siginfo_t) == 8);
static_assert(offsetof(siginfo_t, si_signo)	== 0x00);
static_assert(offsetof(siginfo_t, si_errno)	== 0x04);
static_assert(offsetof(siginfo_t, si_code)	== 0x08);
static_assert(offsetof(siginfo_t, si_addr)	== 0x10);
...
```

这些是**编译期 ABI 契约**：任何改动只要破坏了用户态可见的 siginfo 布局，编译直接失败。

## TLS 与 tpidr_el0

AAPCS64 把 `tpidr_el0` 留给平台 ABI，Linux 用它存放**线程指针**（thread pointer，TP）。用户态 libc 通过 `mrs xN, tpidr_el0` 读取 TP，再按 TLS 变体（local-exec/general-dynamic）偏移得到线程局部变量地址。`set_tid_address`/`clone(CLONE_SETTLS)` 最终都落到这个寄存器。

内核侧的存储位置是 `thread_struct.uw.tp_value`（`arch/arm64/include/asm/processor.h:161`）：

```c
	unsigned long	tp_value;	/* TLS register */
```

上下文切换时由 `tls_thread_switch()`（`arch/arm64/kernel/process.c:530`）保存/恢复：

```c
void tls_preserve_current_state(void)
{
	*task_user_tls(current) = read_sysreg(tpidr_el0);
	if (system_supports_tpidr2() && !is_compat_task())
		current->thread.tpidr2_el0 = read_sysreg_s(SYS_TPIDR2_EL0);
}

static void tls_thread_switch(struct task_struct *next)
{
	tls_preserve_current_state();

	if (is_compat_thread(task_thread_info(next)))
		write_sysreg(next->thread.uw.tp_value, tpidrro_el0);
	else
		write_sysreg(0, tpidrro_el0);

	write_sysreg(*task_user_tls(next), tpidr_el0);
	if (system_supports_tpidr2())
		write_sysreg_s(next->thread.tpidr2_el0, SYS_TPIDR2_EL0);
}
```

三个寄存器的分工：

| 寄存器 | 用途 | 谁写 |
| :-- | :-- | :-- |
| `tpidr_el0` | 64 位任务的线程指针 | 内核在切换时写，用户态可读写 |
| `tpidrro_el0` | 32 位兼容任务的只读 TP；64 位下清 0 | 内核 |
| `tpidr2_el0` | SME 引入的第二线程指针，供 streaming mode 下区分状态 | 内核/用户态 |

注意 `tpidr_el0` 在异常入口还被临时挪用作栈溢出检测的暂存器（`arch/arm64/kernel/entry.S:111` 的 `msr tpidr_el0, x0`），但那是在 `kernel_entry` 保存完用户态值之后，且返回前会恢复，不影响 ABI。

ptrace 的 `NT_ARM_TLS` 视图固定两个槽位（`arch/arm64/kernel/ptrace.c:662`）：

```c
static int tls_get(struct task_struct *target, const struct user_regset *regset,
		   struct membuf to)
{
	int ret;

	if (target == current)
		tls_preserve_current_state();

	ret = membuf_store(&to, target->thread.uw.tp_value);
	if (system_supports_tpidr2())
		ret = membuf_store(&to, target->thread.tpidr2_el0);
	else
		ret = membuf_zero(&to, sizeof(u64));

	return ret;
}
```

不支持 TPIDR2 时第二个槽位填 0 而不是省略——**保持 regset 尺寸恒定**是 ABI 稳定性的要求。

fork 时子进程继承 TP（`arch/arm64/kernel/process.c:442` 附近 `*task_user_tls(p) = read_sysreg(tpidr_el0)`），exec 时清零（`arch/arm64/kernel/process.c:255` 的 `write_sysreg(0, tpidr_el0)`）。

## hwcap 机制

用户态通过 `getauxval(AT_HWCAP)` / `AT_HWCAP2` / `AT_HWCAP3` 或 `/proc/cpuinfo` 的 Features 行探测 CPU 能力。内核侧的真相源是 `arch/arm64/kernel/cpufeature.c:102` 的位图：

```c
static DECLARE_BITMAP(elf_hwcap, MAX_CPU_FEATURES) __read_mostly;
```

注意名字：本树中数组叫 `elf_hwcap`（位图），能力表叫 `arm64_elf_hwcaps[]`（`arch/arm64/kernel/cpufeature.c:3283`），没有名为 `arm64_elf_hwcap` 的单一变量。

能力表用一组宏声明，每条把"ID 寄存器字段 ≥ 某值"映射到一个 HWCAP 位：

```c
#define HWCAP_CPUID_MATCH(reg, field, min_value)			\
		.matches = has_user_cpuid_feature,			\
		ARM64_CPUID_FIELDS(reg, field, min_value)

#define __HWCAP_CAP(name, cap_type, cap)					\
		.desc = name,							\
		.type = ARM64_CPUCAP_SYSTEM_FEATURE,				\
		.hwcap_type = cap_type,						\
		.hwcap = cap,							\

#define HWCAP_CAP(reg, field, min_value, cap_type, cap)		\
	{									\
		__HWCAP_CAP(#cap, cap_type, cap)				\
		HWCAP_CPUID_MATCH(reg, field, min_value) 		\
	}
```

表项举例：

```c

	HWCAP_CAP(ID_AA64ISAR0_EL1, AES, PMULL, CAP_HWCAP, KERNEL_HWCAP_PMULL),
	HWCAP_CAP(ID_AA64ISAR0_EL1, AES, AES, CAP_HWCAP, KERNEL_HWCAP_AES),
	HWCAP_CAP(ID_AA64ISAR0_EL1, ATOMIC, IMP, CAP_HWCAP, KERNEL_HWCAP_ATOMICS),
	HWCAP_CAP(ID_AA64PFR0_EL1, FP, IMP, CAP_HWCAP, KERNEL_HWCAP_FP),
	HWCAP_CAP(ID_AA64PFR0_EL1, AdvSIMD, IMP, CAP_HWCAP, KERNEL_HWCAP_ASIMD),
	HWCAP_CAP(ID_AA64PFR0_EL1, SVE, IMP, CAP_HWCAP, KERNEL_HWCAP_SVE),
	HWCAP_CAP(ID_AA64PFR1_EL1, BT, IMP, CAP_HWCAP, KERNEL_HWCAP_BTI),
	HWCAP_CAP(ID_AA64PFR1_EL1, GCS, IMP, CAP_HWCAP, KERNEL_HWCAP_GCS),
	...
};
```

`ARM64_CPUCAP_SYSTEM_FEATURE` 再次出现——HWCAP 必须是**全系统一致**的，否则进程迁移到不支持该特性的核上就会崩。这与 RAS 笔记里的道理相同。

有些特性需要额外条件，用 `HWCAP_CAP_MATCH_ID` 叠加自定义匹配函数：

```c
#ifdef CONFIG_ARM64_SVE
static bool has_sve_feature(const struct arm64_cpu_capabilities *cap, int scope)
{
	return system_supports_sve() && has_user_cpuid_feature(cap, scope);
}
#endif
```

即：SVE2 之类的 HWCAP 不仅要求 ID 寄存器声明，还要求内核真的启用了 SVE 支持。PAC 则用 `HWCAP_MULTI_CAP` 把 APA/API/APA3 多种实现方式合并成一个 `KERNEL_HWCAP_PACA`（`arch/arm64/kernel/cpufeature.c:3242` 的 `ptr_auth_hwcap_addr_matches[]`）。

初始化流程（`arch/arm64/kernel/cpufeature.c:3514`）：

```c
static void setup_elf_hwcaps(const struct arm64_cpu_capabilities *hwcaps)
{
	/* We support emulation of accesses to CPU ID feature registers */
	cpu_set_named_feature(CPUID);
	for (; hwcaps->matches; hwcaps++)
		if (hwcaps->matches(hwcaps, cpucap_default_scope(hwcaps)))
			cap_set_elf_hwcap(hwcaps);
}
```

`CPUID` 位无条件置位，因为内核会模拟 `mrs` 读 ID 寄存器（见 `arch/arm64/kernel/traps.c` 的 `do_el0_sys`）。最终导出给用户态的是三个 accessor（`arch/arm64/kernel/cpufeature.c:3911`）：

```c
unsigned long cpu_get_elf_hwcap(void)
{
	/*
	 * We currently only populate the first 32 bits of AT_HWCAP. Please
	 * note that for userspace compatibility we guarantee that bits 62
	 * and 63 will always be returned as 0.
	 */
	return elf_hwcap[0];
}

unsigned long cpu_get_elf_hwcap2(void)
{
	return elf_hwcap[1];
}

unsigned long cpu_get_elf_hwcap3(void)
{
	return elf_hwcap[2];
}
```

注释里"bit 62/63 恒为 0"是一条明确的 ABI 承诺——历史上某些 libc 用这两位做别的事。

CPU 热插拔时还会做一致性校验（`arch/arm64/kernel/cpufeature.c:3714` 的 `__verify_local_elf_hwcaps`）：若新上线的 CPU 不支持已宣告的 HWCAP，内核会拒绝该 CPU 或触发 sanity check，防止用户态在迁移后踩空。

## PAC/BTI 对 ABI 的影响

### 内核自身的编译选项

`arch/arm64/Makefile:81` 按配置选择分支保护策略：

```make

  KBUILD_CFLAGS += -mbranch-protection=pac-ret+bti
  KBUILD_RUSTFLAGS += -Zbranch-protection=bti,pac-ret
else ifeq ($(CONFIG_ARM64_PTR_AUTH_KERNEL),y)
  KBUILD_RUSTFLAGS += -Zbranch-protection=pac-ret
  ifeq ($(CONFIG_CC_HAS_BRANCH_PROT_PAC_RET),y)
    KBUILD_CFLAGS += -mbranch-protection=pac-ret
  else
    KBUILD_CFLAGS += -msign-return-address=non-leaf
  endif
else
  KBUILD_CFLAGS += $(call cc-option,-mbranch-protection=none)

```

本树 `.config`：`CONFIG_ARM64_PTR_AUTH_KERNEL=y`、`CONFIG_CC_HAS_BRANCH_PROT_PAC_RET=y`、`CONFIG_ARM64_BTI_KERNEL` 未启用、`CONFIG_CC_HAS_BRANCH_PROT_PAC_RET_BTI=y`（工具链支持但内核未开）。因此实际走的是 **`-mbranch-protection=pac-ret`** 这一支：编译器在每个非叶函数的序言插入 `paciasp`、尾声插入 `autiasp`，用 APIAKey 对返回地址签名。

`-mbranch-protection=pac-ret` 不改变参数传递约定，但改变了**栈帧内容**：LR 槽里存的是带 PAC 的指针。调试器/unwinder 必须知道这一点，内核提供了 `ptrauth_strip_kernel_insn_pac()` 用于打印（`arch/arm64/kernel/process.c:224`）。

另一条与 x18 相关的选项在 `arch/arm64/Makefile:117`：

```make
ifeq ($(CONFIG_SHADOW_CALL_STACK), y)
KBUILD_CFLAGS	+= -ffixed-x18
KBUILD_RUSTFLAGS += -Zfixed-x18
endif
```

AAPCS64 把 x18 留作"平台寄存器"。Linux 在启用影子调用栈时把它固定为 SCS 指针，编译器不再分配它。**本树 `CONFIG_SHADOW_CALL_STACK` 未启用**，所以 x18 在内核里仍是普通临时寄存器。

### 用户态密钥管理

每个进程有自己的一套 PAC 密钥，线程间共享，fork 继承、exec 重置（`arch/arm64/include/asm/pointer_auth.h:32` 的注释）：

```c
struct ptrauth_keys_user {
	struct ptrauth_key apia;
	struct ptrauth_key apib;
	struct ptrauth_key apda;
	struct ptrauth_key apdb;
	struct ptrauth_key apga;
};
```

五把密钥：APIA/APIB 用于指令地址（返回地址），APDA/APDB 用于数据地址，APGA 用于通用认证。初始化（`arch/arm64/include/asm/pointer_auth.h:86`）：

```c
static inline void ptrauth_keys_init_user(struct ptrauth_keys_user *keys)
{
	if (system_supports_address_auth()) {
		get_random_bytes(&keys->apia, sizeof(keys->apia));
		get_random_bytes(&keys->apib, sizeof(keys->apib));
		get_random_bytes(&keys->apda, sizeof(keys->apda));
		get_random_bytes(&keys->apdb, sizeof(keys->apdb));
	}

	if (system_supports_generic_auth())
		get_random_bytes(&keys->apga, sizeof(keys->apga));

	ptrauth_keys_install_user(keys);
}
```

exec 时由 `ptrauth_thread_init_user()` 宏调用（`arch/arm64/kernel/process.c:868`），并默认启用全部四把地址密钥：

```c
#define ptrauth_thread_init_user()                                             \
	do {                                                                   \
		ptrauth_keys_init_user(&current->thread.keys_user);            \
									       \
		/* enable all keys */                                          \
		if (system_supports_address_auth())                            \
			ptrauth_set_enabled_keys(current,                      \
						 PR_PAC_ENABLED_KEYS_MASK,     \
						 PR_PAC_ENABLED_KEYS_MASK);    \
	} while (0)
```

上下文切换只安装 APIB/APDA/APDB/APGA（`ptrauth_keys_install_user`），**APIA 留给内核自己用**（`CONFIG_ARM64_PTR_AUTH_KERNEL`），避免用户态密钥与内核密钥互相干扰。

用户态通过 `prctl(PR_PAC_RESET_KEYS, ...)` 重置密钥、`PR_PAC_SET_ENABLED_KEYS`/`PR_PAC_GET_ENABLED_KEYS` 控制启用位。这些是 ABI 的一部分，声明在 `arch/arm64/include/asm/pointer_auth.h:101`。

### BTI

BTI（Branch Target Identification）要求间接跳转的目标必须是 `bti c`/`bti j`/`bti jc` 或 `paciasp` 等"着陆垫"指令。内核在两个地方与之交互：

1. **信号投递**：`setup_return()` 设 `PSR_BTYPE_C`，模拟 BLR（见前文）。
2. **系统调用返回**：`el0_svc_common()` 故意不清 BTYPE（见前文注释）。

用户态通过 `mprotect(PROT_BTI)` 标记受保护页，内核在 `arch/arm64/mm/fault.c` 的 `do_el0_bti()` 里把违规转成 SIGILL。HWCAP 中的 `KERNEL_HWCAP_BTI` 由 `ID_AA64PFR1_EL1.BT` 决定。

## SVE/SME 状态与 ABI

SVE（Scalable Vector Extension）与 SME（Scalable Matrix Extension）给 ABI 带来的最大变化是：**向量寄存器宽度不再固定**。Z0-Z31 的宽度由向量长度 VL 决定，VL 是 128 位的整数倍，进程可以通过 `prctl(PR_SVE_SET_VL)` 选择。

内核用 `thread.fp_type` 区分当前保存的是哪种状态（`arch/arm64/kernel/fpsimd.c:322` 附近的注释）：

```c
/*
 *    When the FPSIMD only state stored task->thread.fp_type is set to
 *    FP_STATE_FPSIMD ...
 *    When the full SVE state is stored task->thread.fp_type is set to
 *    FP_STATE_SVE ...
 */
```

首次执行 SVE 指令会触发 trap，由 `do_sve_acc()`（`arch/arm64/kernel/fpsimd.c:1311`）惰性分配状态：

```c
void do_sve_acc(unsigned long esr, struct pt_regs *regs)
{
	/* Even if we chose not to use SVE, the hardware could still trap: */
	if (unlikely(!system_supports_sve()) || WARN_ON(is_compat_task())) {
		force_signal_inject(SIGILL, ILL_ILLOPC, regs->pc, 0);
		return;
	}

	sve_alloc(current, true);
	if (!current->thread.sve_state) {
		force_sig(SIGKILL);
		return;
	}

	get_cpu_fpsimd_context();

	if (test_and_set_thread_flag(TIF_SVE))
		WARN_ON(1); /* SVE access shouldn't have trapped */
	...
}
```

这种"trap-on-first-use"避免了给每个进程都分配可能高达数 KB 的 SVE 状态。

**系统调用对 SVE/SME 状态的破坏是 ABI 明文规定的**。`fpsimd_syscall_enter()`（`arch/arm64/kernel/entry-common.c:244`）：

```c
static inline void fpsimd_syscall_enter(void)
{
	/* Ensure PSTATE.SM is clear, but leave PSTATE.ZA as-is. */
	if (system_supports_sme())
		sme_smstop_sm();

	if (!system_supports_sve())
		return;

	if (test_thread_flag(TIF_SVE))
		sve_flush_live();

	__this_cpu_write(fpsimd_last_state.to_save, FP_STATE_FPSIMD);
}
```

即：进入系统调用时退出 streaming mode（SM=0），把 SVE 中不与 FPSIMD 共享的高位清零；ZA 保持不变。返回时 `fpsimd_syscall_exit()` 把 `to_save` 恢复成 `FP_STATE_CURRENT`，结束惰性丢弃。用户态若想在系统调用后继续用 SVE 高位，必须自己重新加载——这是 AAPCS64 的 caller-saved 语义在系统调用边界上的体现。

信号帧中的 SVE/ZA/ZT 记录见前文"信号帧布局"。ptrace 侧对应 `NT_ARM_SVE`/`NT_ARM_SSVE`/`NT_ARM_ZA`/`NT_ARM_ZT`，它们的 `.size = SVE_VQ_BYTES`（16 字节），`.n` 按最大 VQ 计算，实际有效长度由记录头里的 VL 字段描述。

## 配置与调试

| 配置项 | 本树状态 | 对 ABI 的影响 |
| :-- | :-- | :-- |
| `CONFIG_ARM64_PTR_AUTH` | y | 用户态 PAC 密钥、`NT_ARM_PAC_*` regset |

| `CONFIG_ARM64_TAGGED_ADDR_ABI` | y | TBI 用户态 ABI、`NT_ARM_TAGGED_ADDR_CTRL` |
| `CONFIG_ARM64_POE` / `GCS` | y / y | POR_EL0、Guarded Control Stack |
| `CONFIG_COMPAT` | **未启用** | 无 AArch32 兼容任务，`compat_sys_call_table` 不编译 |
| `CONFIG_CHECKPOINT_RESTORE` | **未启用** | PAC 密钥值 regset 不可用 |
| `CONFIG_SHADOW_CALL_STACK` | 未启用 | x18 未被固定 |
| `CONFIG_STACKPROTECTOR_PER_TASK` | y | 用 `sp_el0` 作栈保护 guard 寄存器 |
| `CONFIG_HAVE_HW_BREAKPOINT` | y | `NT_ARM_HW_BREAK/WATCH` regset |

调试切入点：

- **strace** 走的是 `syscall_trace_enter`/`syscall_trace_exit` 路径，依赖 `orig_x0` 与 `syscallno` 字段。
- **gdb** 通过 `PTRACE_GETREGSET` + `NT_PRSTATUS`/`NT_PRFPREG` 取寄存器，通过 `NT_ARM_TLS` 取 TP。
- **core dump** 由 `user_regset_view` 的 `.core_note_type` 决定哪些 regset 进 ELF note。
- **`/proc/cpuinfo`** 的 Features 行由 `arch/arm64/kernel/cpuinfo.c` 遍历 hwcap 位图生成。
- **`AT_MINSIGSTKSZ`** 由 `minsigstksz_setup()`（`arch/arm64/kernel/signal.c:1704`）按 `add_all=true` 的最大帧算出，用户态据此分配 sigaltstack。
