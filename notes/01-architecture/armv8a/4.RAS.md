## Cache ECC and parity

## Cache protection behavior
**Single Error Detect (SED)**
**Single Error Correct, Double Error Detect (SECDED)**
## Uncorrected errors and data poisoning
如果检测到错误，纠正部件会触发。但是，2-bit ECC错误不能纠正。
## RAS error types
**Corrected error (CE)**
错误被检测并纠正，不会影响node状态，不会静默传播，node继续运行。
**Deferred error (DE)**
错误被检测但是不能被纠正，可被延迟。错误不会静默传播但是会潜伏在系统，node继续运行。
**Uncorrected Error (UC)**
错误被检测但是不能纠正不能延迟。错误潜伏在系统。
**node产生的不可纠正错误**
Latent： 错误未传播，错误被检测但未被消费，并且未被记录为DE。
Signaled： 错误未传播，但是可能被消费，并且未被记录为DE。
Unrecoverable (UEU)：错误未静默传播，node不能继续运行。
Uncontainable (UC)：错误可能已静默传播，错误如果不能被隔离，必须关闭系统避免灾难性错误。
**Errors consumed at the node**
被node消费的不可纠正错误，子类型：
Restartable (UEO)：错误未静默传播。node因为消费了一个错误而停止运算。该节点因为不依赖损坏的数据而可以继续运行。
Recoverable (UER)：错误并未被静默传播。 节点停止运行。 要继续，节点依赖于使用损坏的数据。 如果软件可以定位并修复错误，则停止的操作可以继续。
Unrecoverable (UEU): 错误尚未以静默方式传播。节点将暂停操作，并且无法从其暂停状态恢复。
Uncontainable (UC): 错误可能已被静默传播。如果无法隔离错误，则必须关闭系统以避免灾难性故障。

## 内核侧 RAS 实现总览

上面几节是 ARM RAS 规格的分类学摘译。落到 Linux 里，这套分类并不是一个独立的"RAS 子系统"，而是被拆成三条互相衔接的路径：

| 路径 | 触发方式 | 内核入口 | 主要源码 |
| :-- | :-- | :-- | :-- |
| 异步 SError | 外部 abort / 延迟错误被消费 | `el1h_64_error_handler`、`el0t_64_error_handler` | `arch/arm64/kernel/entry-common.c`、`arch/arm64/kernel/traps.c` |
| 同步外部中止 SEA | 取指/访存命中外部错误 | `do_sea` | `arch/arm64/mm/fault.c` |
| 固件优先（firmware-first） | 固件把错误写成 CPER 记录再通知内核 | `ghes_notify_sea` / `ghes_proc` | `drivers/acpi/apei/ghes.c` |

三者的共同点是：硬件只负责"报告"，严重性判定与恢复决策全部在内核。规格里的 CE/DE/UEO/UER/UEU/UC 在内核中被压缩成两个问题——**这个错误是不是 RAS 编码的**、**CPU 还能不能继续往前走**。前者由 `arm64_is_ras_serror()` 回答，后者由 `arm64_is_fatal_ras_serror()` 回答。

本树 `.config` 中 `CONFIG_ARM64_RAS_EXTN=y`、`CONFIG_RAS=y`，但 `CONFIG_ACPI` 未启用、`CONFIG_MEMORY_FAILURE` 未启用、`CONFIG_ARM_SDE_INTERFACE` 未启用。因此下文凡是涉及 GHES/APEI 的部分，都属于"源码存在，当前配置未启用"，实际运行时走的是纯架构路径（SError 直接 panic、SEA 直接给进程发信号）。

## ARM64 RAS 扩展与特性检测

### ID_AA64PFR0_EL1.RAS 与 cpufeature

RAS 扩展是否存在，由 `ID_AA64PFR0_EL1` 的 RAS 字段（bit[31:28]）描述。`arch/arm64/kernel/cpufeature.c` 把它登记进 ftr 寄存器表：

```c
/* arch/arm64/kernel/cpufeature.c:302 */
ARM64_FTR_BITS(FTR_HIDDEN, FTR_STRICT, FTR_LOWER_SAFE, ID_AA64PFR0_EL1_RAS_SHIFT, 4, 0),
```

`FTR_STRICT` 表示异构系统上各 CPU 的该字段必须一致，否则内核会报 sanity check 失败；`FTR_LOWER_SAFE` 表示取系统内最小值作为安全值——只要有一个核不支持 RAS，整机就按不支持处理。

对应的 capability 条目在 `arm64_features[]` 中（`arch/arm64/kernel/cpufeature.c:2697` 起）：

```c
#ifdef CONFIG_ARM64_RAS_EXTN
	{
		.desc = "RAS Extension Support",
		.capability = ARM64_HAS_RAS_EXTN,
		.type = ARM64_CPUCAP_SYSTEM_FEATURE,
		.matches = has_cpuid_feature,
		.cpu_enable = cpu_clear_disr,
		ARM64_CPUID_FIELDS(ID_AA64PFR0_EL1, RAS, IMP)
	},
	{
		.desc = "RASv1p1 Extension Support",
		.capability = ARM64_HAS_RASV1P1_EXTN,
		.type = ARM64_CPUCAP_SYSTEM_FEATURE,
		.matches = has_rasv1p1,
	},
#endif /* CONFIG_ARM64_RAS_EXTN */
```

两个要点：

1. `ARM64_CPUCAP_SYSTEM_FEATURE` 意味着这是"系统级"特性，需要所有在线 CPU 都满足才置位，与 `ARM64_CPUCAP_LOCAL_CPU_FEATURE` 那类"每核独立"的特性不同。SError 的严重性解读依赖全系统一致的 RAS 语义，所以必须是系统级。
2. `.cpu_enable = cpu_clear_disr` 是每个 CPU 上线时都要执行的钩子，负责清掉固件可能遗留的延迟错误：

```c
/* arch/arm64/kernel/cpufeature.c:2188 */
static void cpu_clear_disr(const struct arm64_cpu_capabilities *__unused)
{
	/* Firmware may have left a deferred error in this register. */
	write_sysreg_s(0, SYS_DISR_EL1);
}
```

RASv1p1 的判定更绕一点，`has_rasv1p1()`（`arch/arm64/kernel/cpufeature.c:2193`）接受两种组合：要么 `ID_AA64PFR0_EL1.RAS == V1P1` 直接声明，要么 `RAS == IMP` 且 `ID_AA64PFR1_EL1.RAS_frac == RASv1p1` 用分数域补充声明。这是因为 RASv1.1 引入时 ID 寄存器的主字段已经用尽，只能靠 `RAS_frac` 扩展表达。

### ESB 错误同步屏障

ESB（Error Synchronization Barrier）是 RAS 扩展引入的 hint 指令，作用是**把当前 PE 上所有"已发生但尚未被同步"的异步错误逼出来**：执行 ESB 之后，任何在 ESB 之前产生的可同步错误要么已经作为 SError 被 taken，要么其状态被记录进 `DISR_EL1`。这样内核就能在一个确定的点上"收账"，而不是让错误在任意后续指令处随机爆出来。

宏定义在 `arch/arm64/include/asm/assembler.h:79`：

```asm
/*
 * RAS Error Synchronization barrier
 */
	.macro  esb
#ifdef CONFIG_ARM64_RAS_EXTN
	hint    #16
#else
	nop
#endif
	.endm
```

`hint #16` 就是 ESB 的编码（见 `arch/arm64/include/asm/insn.h` 中的 `AARCH64_INSN_HINT_ESB = 0x10 << 5`）。在不支持 RAS 的 CPU 上它退化为 nop，因此可以无条件插入。

**本树的一个重要事实**：`arch/arm64/kernel/entry.S` 中已经**没有**显式的 `esb` 指令了。全树 grep 下来，`esb` 宏的实际使用者只剩 KVM 的 hyp 向量（`arch/arm64/kvm/hyp/hyp-entry.S:154` 与 `:218`）。内核自身的异常入口改为依赖 **SCTLR_EL1.IESB（Implicit ESB）**——由硬件在每次异常进入时自动执行一次等效的 ESB。

IESB 位定义在 `arch/arm64/include/asm/sysreg.h:827`：

```c
#define SCTLR_ELx_IESB	 (BIT(21))
```

它被无条件包含在 `INIT_SCTLR_EL1_MMU_ON`（`arch/arm64/include/asm/sysreg.h:863`）里：

```c
#define INIT_SCTLR_EL1_MMU_ON \
	(SCTLR_ELx_M      | SCTLR_ELx_C      | SCTLR_ELx_SA    | \
	 SCTLR_EL1_SA0    | SCTLR_EL1_SED    | SCTLR_ELx_I     | \
	 SCTLR_EL1_DZE    | SCTLR_EL1_UCT    | SCTLR_EL1_nTWE  | \
	 SCTLR_ELx_IESB   | SCTLR_EL1_SPAN   | SCTLR_ELx_ITFSB | \
	 ENDIAN_SET_EL1   | SCTLR_EL1_UCI    | SCTLR_EL1_EPAN  | \
	 SCTLR_EL1_LSMAOE | SCTLR_EL1_nTLSMD | SCTLR_EL1_EIS   | \
	 SCTLR_EL1_TSCXT  | SCTLR_EL1_EOS)
```

这个常量在 `__cpu_setup` 末尾装入 x0（`arch/arm64/mm/proc.S:569`），再由 `head.S` 的 `set_sctlr_el1` 写入寄存器。不支持 RAS 的 CPU 上 IESB 是 RES0，写 1 无副作用，所以不需要 alternative 补丁。

IESB 的能力由 `ID_AA64MMFR2_EL1.IESB` 描述，cpufeature 中同样以 `FTR_HIDDEN/FTR_NONSTRICT/FTR_LOWER_SAFE` 登记（`arch/arm64/kernel/cpufeature.c:507`）。

### DISR_EL1 与延迟错误

`DISR_EL1`（Deferred Interrupt Status Register）是 ESB 的"收据"。如果 ESB 逼出了一个错误但当时 SError 被屏蔽（PSTATE.A=1），错误不会丢，而是把 syndrome 存进 DISR_EL1，等内核方便时再读。

寄存器编码在 `arch/arm64/include/asm/sysreg.h:369`：

```c
#define SYS_DISR_EL1			sys_reg(3, 0, 12, 1, 1)
```

DISR 与 ESR 的位布局刻意做了兼容，`arch/arm64/include/asm/esr.h:197` 给出转换掩码：

```c
#define DISR_EL1_IDS		(UL(1) << 24)
/*
 * DISR_EL1 and ESR_ELx share the bottom 13 bits, but the RES0 bits may mean
 * different things in the future...
 */
#define DISR_EL1_ESR_MASK	(ESR_ELx_AET | ESR_ELx_EA | ESR_ELx_FSC)
```

`arch/arm64/include/asm/exception.h:17` 的 `disr_to_esr()` 负责把 DISR 还原成一个"伪造的 ESR"，好让下游的 `do_serror()` 逻辑复用：

```c
static inline unsigned long disr_to_esr(u64 disr)
{
	unsigned long esr = ESR_ELx_EC_SERROR << ESR_ELx_EC_SHIFT;

	if ((disr & DISR_EL1_IDS) == 0)
		esr |= (disr & DISR_EL1_ESR_MASK);
	else
		esr |= (disr & ESR_ELx_ISS_MASK);

	return esr;
}
```

IDS（Implementation Defined Syndrome）位为 0 说明是标准 RAS 编码，只取 AET/EA/FSC 三个字段；为 1 说明是实现自定义 syndrome，整段 ISS 原样搬过去。

除了 `cpu_clear_disr()`，CPU 从低功耗状态恢复时也要清一次，见 `arch/arm64/mm/proc.S:168`：

```asm
alternative_if ARM64_HAS_RAS_EXTN
	msr_s	SYS_DISR_EL1, xzr
alternative_else_nop_endif
```

这里用 alternative 而不是无条件写，是因为 `cpu_do_resume` 运行在 MMU 刚恢复的敏感窗口，不支持 RAS 的 CPU 上访问该寄存器会触发未定义指令异常。

## SError 处理路径

### 异常向量与入口

SError 在异常向量表里占的是每组第 4 个槽位（offset 0x180/0x380/0x580/0x780），标签为 `error`。`arch/arm64/kernel/entry.S:591` 起的 `vectors`：

```asm
SYM_CODE_START(vectors)
	kernel_ventry	1, t, 64, sync		// Synchronous EL1t
	kernel_ventry	1, t, 64, irq		// IRQ EL1t
	kernel_ventry	1, t, 64, fiq		// FIQ EL1t
	kernel_ventry	1, t, 64, error		// Error EL1t

	kernel_ventry	1, h, 64, sync		// Synchronous EL1h
	kernel_ventry	1, h, 64, irq		// IRQ EL1h
	kernel_ventry	1, h, 64, fiq		// FIQ EL1h
	kernel_ventry	1, h, 64, error		// Error EL1h
	...
```

`entry_handler` 宏（`arch/arm64/kernel/entry.S:642`）把每个槽位展开成 `el1h_64_error` 这样的汇编 stub：保存 GPR → `mov x0, sp` → `bl el1h_64_error_handler` → `ret_to_kernel`/`ret_to_user`。

C 侧入口在 `arch/arm64/kernel/entry-common.c:535`：

```c
asmlinkage void noinstr el1h_64_error_handler(struct pt_regs *regs)
{
	unsigned long esr = read_sysreg(esr_el1);
	irqentry_state_t state;

	local_daif_restore(DAIF_ERRCTX);
	state = irqentry_nmi_enter(regs);
	do_serror(regs, esr);
	irqentry_nmi_exit(regs, state);
}
```

三个细节值得注意：

- `DAIF_ERRCTX` 定义在 `arch/arm64/include/asm/daifflags.h:17`，值为 `PSR_A_BIT | PSR_I_BIT | PSR_F_BIT`，即**同时屏蔽 SError、IRQ、FIQ**。SError 处理期间不能再被 SError 打断，否则错误状态会被覆盖。
- 走的是 `irqentry_nmi_enter()` 而非普通 `irqentry_enter()`。SError 被当作 NMI 类上下文处理，这样即使它打断了关中断的临界区，printk/lockdep 也能正确标注。
- 从 EL0 来的 SError 走 `__el0_error_handler_common()`（`arch/arm64/kernel/entry-common.c:854`），多了一层 `arm64_enter_from_user_mode()` / `arm64_exit_to_user_mode()`，后者会处理 task_work、信号与调度。

### ESR 编码：IDS / AET / DFSC

`arch/arm64/include/asm/esr.h:90` 起定义了 SError 的 ISS 布局：

```c
/* Asynchronous Error Type */
#define ESR_ELx_IDS_SHIFT	(24)
#define ESR_ELx_IDS		(UL(1) << ESR_ELx_IDS_SHIFT)
#define ESR_ELx_AET_SHIFT	(10)
#define ESR_ELx_AET		(UL(0x7) << ESR_ELx_AET_SHIFT)

#define ESR_ELx_AET_UC		(UL(0) << ESR_ELx_AET_SHIFT)
#define ESR_ELx_AET_UEU		(UL(1) << ESR_ELx_AET_SHIFT)
#define ESR_ELx_AET_UEO		(UL(2) << ESR_ELx_AET_SHIFT)
#define ESR_ELx_AET_UER		(UL(3) << ESR_ELx_AET_SHIFT)
#define ESR_ELx_AET_CE		(UL(6) << ESR_ELx_AET_SHIFT)
```

与本文开头规格分类的对应关系：

| AET 编码 | 规格术语 | 内核判定 | 后果 |
| :-- | :-- | :-- | :-- |
| 0b000 (0) | UC / Uncontainable | 致命 | 直接 `arm64_serror_panic()` |
| 0b001 (1) | UEU / Unrecoverable | 致命 | `do_serror` 返回后 panic |
| 0b010 (2) | UEO / Restartable | 非致命 | 忽略，继续运行 |
| 0b011 (3) | UER / Recoverable | 致命 | panic（异常可能不精确） |
| 0b110 (6) | CE / Corrected | 非致命 | 忽略，继续运行 |

注意 UER 在规格上是"可恢复"的，但 Linux 一律按致命处理。原因写在 `arm64_is_fatal_ras_serror()` 的注释里：SError 是异步的，可能已经 imprecise，内核无法定位到究竟哪条指令消费了坏数据；再加上 Neoverse-N1 #1349291 勘误要求把非 KVM 场景下报为 Unrecoverable 的错误当作 Uncontainable，两者合并成同一条 panic 路径。

另外，AET 字段只有在 DFSC == `ESR_ELx_FSC_SERROR`（0x11，`arch/arm64/include/asm/esr.h:120`）时才有效，否则是 RES0。

### do_serror 与致命性判定

判定逻辑分两层。第一层在头文件里做纯位运算（`arch/arm64/include/asm/traps.h:68`）：

```c
static inline bool arm64_is_ras_serror(unsigned long esr)
{
	WARN_ON(preemptible());

	if (esr & ESR_ELx_IDS)
		return false;

	if (this_cpu_has_cap(ARM64_HAS_RAS_EXTN))
		return true;
	else
		return false;
}
```

IDS 位在没有 RAS 的 CPU 上叫 ISV（ISS Valid），语义正好相反：置位表示 syndrome 有效但**不是** RAS 编码。所以"IDS=1 → 不是 RAS 错误"这条判断在两种 CPU 上都成立。`WARN_ON(preemptible())` 是因为 `this_cpu_has_cap()` 依赖当前 CPU 编号稳定。

第二层取严重性（`arch/arm64/include/asm/traps.h:88`）：

```c
static inline unsigned long arm64_ras_serror_get_severity(unsigned long esr)
{
	unsigned long aet = esr & ESR_ELx_AET;

	if (!arm64_is_ras_serror(esr)) {
		/* Not a RAS error, we can't interpret the ESR. */
		return ESR_ELx_AET_UC;
	}

	if ((esr & ESR_ELx_FSC) != ESR_ELx_FSC_SERROR) {
		/* No severity information : Uncategorized */
		return ESR_ELx_AET_UC;
	}

	return aet;
}
```

**无法解读就按最坏情况处理**——这是 RAS 代码的一贯保守策略。

最终的决策函数在 `arch/arm64/kernel/traps.c:947`：

```c
bool arm64_is_fatal_ras_serror(struct pt_regs *regs, unsigned long esr)
{
	unsigned long aet = arm64_ras_serror_get_severity(esr);

	switch (aet) {
	case ESR_ELx_AET_CE:	/* corrected error */
	case ESR_ELx_AET_UEO:	/* restartable, not yet consumed */
		return false;

	case ESR_ELx_AET_UEU:	/* Uncorrected Unrecoverable */
	case ESR_ELx_AET_UER:	/* Uncorrected Recoverable */
		return true;

	case ESR_ELx_AET_UC:	/* Uncontainable or Uncategorized error */
	default:
		/* Error has been silently propagated */
		arm64_serror_panic(regs, esr);
	}
}
```

UC 分支直接就地 panic 而不是返回 true，因为错误可能已经静默传播，多执行一条指令都是风险。

顶层入口极简（`arch/arm64/kernel/traps.c:979`）：

```c
void do_serror(struct pt_regs *regs, unsigned long esr)
{
	/* non-RAS errors are not containable */
	if (!arm64_is_ras_serror(esr) || arm64_is_fatal_ras_serror(regs, esr))
		arm64_serror_panic(regs, esr);
}
```

panic 函数本身（`arch/arm64/kernel/traps.c:932`）会打上 `TAINT_MACHINE_CHECK` 标记、提升 console  verbosity、打印 ESR 与寄存器现场，然后 `nmi_panic()`：

```c
void __noreturn arm64_serror_panic(struct pt_regs *regs, unsigned long esr)
{
	add_taint(TAINT_MACHINE_CHECK, LOCKDEP_STILL_OK);
	console_verbose();

	pr_crit("SError Interrupt on CPU%d, code 0x%016lx -- %s\n",
		smp_processor_id(), esr, esr_get_class_string(esr));
	if (regs)
		__show_regs(regs);

	nmi_panic(regs, "Asynchronous SError Interrupt");

	cpu_park_loop();
}
```

用 `nmi_panic()` 而非 `panic()` 是为了在 NMI 上下文里安全地停住其他 CPU；`cpu_park_loop()` 是最后的兜底，让本核停在 wfe/wfi 循环里。

### 调用链

```
硬件外部 abort / 延迟错误被消费
  → （IESB 隐式屏障或 esb 指令同步）
  → vectors 第 4 槽 kernel_ventry 1, h, 64, error
  → el1h_64_error（entry_handler 展开）
  → el1h_64_error_handler()            [entry-common.c]
      local_daif_restore(DAIF_ERRCTX)  // 屏蔽 A/I/F
      irqentry_nmi_enter()
  → do_serror()                        [traps.c]
  → arm64_is_ras_serror()              [traps.h]
  → arm64_ras_serror_get_severity()    [traps.h]
  → arm64_is_fatal_ras_serror()        [traps.c]
  → arm64_serror_panic() → nmi_panic() → cpu_park_loop()
```

EL0 来源的分支把 `el1h_64_error_handler` 换成 `__el0_error_handler_common`，其余相同。

## 同步外部中止（SEA）与 firmware-first

SError 是异步的，而**同步外部中止**（Synchronous External Abort，SEA）是精确的：它绑定到具体那条访存指令，FAR_EL1 给出出错地址。SEA 走的是 data abort / instruction abort 向量，最终落到 `do_mem_abort()` 的 fault_info 分派表。

`arch/arm64/mm/fault.c:930` 起的表项把 DFSC 0x10（synchronous external abort）以及各级 translation table walk 的外部 abort 都指向 `do_sea`：

```c
{ do_sea,		SIGBUS,  BUS_OBJERR,	"synchronous external abort"	},
...
{ do_sea,		SIGBUS,  BUS_OBJERR,	"synchronous parity or ECC error" },	// Reserved when RAS is implemented
```

`do_sea()`（`arch/arm64/mm/fault.c:866`）：

```c
static int do_sea(unsigned long far, unsigned long esr, struct pt_regs *regs)
{
	const struct fault_info *inf;
	unsigned long siaddr;

	inf = esr_to_fault_info(esr);

	if (user_mode(regs) && apei_claim_sea(regs) == 0) {
		/*
		 * APEI claimed this as a firmware-first notification.
		 * Some processing deferred to task_work before ret_to_user().
		 */
		return 0;
	}

	if (esr & ESR_ELx_FnV) {
		siaddr = 0;
	} else {
		siaddr  = untagged_addr(far);
	}
	add_taint(TAINT_MACHINE_CHECK, LOCKDEP_STILL_OK);
	arm64_notify_die(inf->name, regs, inf->sig, inf->code, siaddr, esr);

	return 0;
}
```

两条分支：

- **firmware-first 认领成功**：固件已经通过 APEI 把错误详情写成 CPER 记录，内核只需把后续处理（如 memory_failure）挂到 task_work，返回用户态前执行，进程可能收到精确的 SIGBUS。
- **无人认领**：内核自己处理。`ESR_ELx_FnV`（FAR not Valid）置位时地址不可信，siaddr 填 0；否则去掉 MTE/TBI tag 位后作为 si_addr。然后按 fault_info 表发 SIGBUS 或 SIGKILL。

`apei_claim_sea()` 的实现（`arch/arm64/kernel/acpi.c:389`）展示了 SEA 与 SError 的优先级纠缠：

```c
	current_flags = local_daif_save_flags();
	return_to_irqs_enabled = !irqs_disabled_flags(arch_local_save_flags());
	if (regs)
		return_to_irqs_enabled = !regs_irqs_disabled(regs);

	/*
	 * SEA can interrupt SError, mask it and describe this as an NMI so
	 * that APEI defers the handling.
	 */
	local_daif_restore(DAIF_ERRCTX);
	nmi_enter();
	err = ghes_notify_sea();
	nmi_exit();
```

SEA 可以打断正在处理的 SError，所以这里必须再次屏蔽 A 位并进入 NMI 上下文。若被中断的代码本身关着中断，irq_work 无法立即执行，只能返回 `-EINPROGRESS` 并打印 "APEI work queued but not completed"。

**当前配置下的实际行为**：`CONFIG_ACPI` 未启用，`arch/arm64/kernel/Makefile:55` 的 `obj-$(CONFIG_ACPI) += acpi.o` 不生效，`arch/arm64/include/asm/acpi.h:124` 提供空桩：

```c
static inline int apei_claim_sea(struct pt_regs *regs) { return -ENOENT; }
```

于是 `do_sea()` 永远走第二条分支，直接给进程发信号。GHES 源码存在，当前配置未启用。

## APEI/GHES 错误记录处理

> 本节内容对应 `CONFIG_ACPI_APEI_GHES`，源码存在，当前配置未启用。

### struct ghes

每个 Generic Hardware Error Source 对应一个 `struct ghes`（`include/acpi/ghes.h:18`）：

```c
struct ghes {
	union {
		struct acpi_hest_generic *generic;
		struct acpi_hest_generic_v2 *generic_v2;
	};
	struct acpi_hest_generic_status *estatus;
	unsigned int estatus_length;
	unsigned long flags;
	union {
		struct list_head list;
		struct timer_list timer;
		unsigned int irq;
	};
	struct device *dev;
	struct list_head elist;
	void __iomem *error_status_vaddr;
};
```

`generic` 指向 ACPI HEST 表里的错误源描述，`estatus` 是固件写错误记录的共享内存缓冲区。那个 union 很关键：同一个 `struct ghes` 根据通知方式不同，要么挂在链表上（NMI/SEA/SDEI 这类共享通知），要么自带 timer（POLLED），要么记录 irq 号（EXTERNAL/GSIV）。

严重性枚举（`include/acpi/ghes.h:50`）把 CPER 的四级映射成内核内部等级：

```c
enum {
	GHES_SEV_NO = 0x0,
	GHES_SEV_CORRECTED = 0x1,
	GHES_SEV_RECOVERABLE = 0x2,
	GHES_SEV_PANIC = 0x3,
};
```

转换函数 `ghes_severity()`（`drivers/acpi/apei/ghes.c:324`）对未知值一律返回 `GHES_SEV_PANIC`，同样是保守策略。

### 通知类型与注册

`ghes_probe()`（`drivers/acpi/apei/ghes.c:1663`）按 `notify.type` 分派：

| 通知类型 | 含义 | 注册动作 |
| :-- | :-- | :-- |
| `ACPI_HEST_NOTIFY_POLLED` | 内核定时轮询 | 建 timer，周期读 estatus |
| `ACPI_HEST_NOTIFY_EXTERNAL` / `SCI` / `GSIV` / `GPIO` | 普通中断 | 申请 irq，`ghes_irq_func` |
| `ACPI_HEST_NOTIFY_SEA` | 同步外部中止 | 挂入 `ghes_sea` 链表 |
| `ACPI_HEST_NOTIFY_NMI` | 不可屏蔽中断 | 挂入 `ghes_nmi` 链表，注册 NMI handler |
| `ACPI_HEST_NOTIFY_SOFTWARE_DELEGATED` | SDEI | `apei_sdei_register_ghes()` |

`is_hest_sync_notify()`（`drivers/acpi/apei/ghes.c:117`）只认 SEA 为同步通知，这个布尔值一路传到 `ghes_do_proc()` 的 `sync` 参数，决定 memory_failure 是否带 `MF_ACTION_REQUIRED`、以及无人处理时是否 `force_sig(SIGBUS)`。

NMI/SEA 这类通知可能在任意 CPU 上、任意上下文里到达，不能睡眠、不能 ioremap。GHES 的解法是 **fixmap + gen_pool**：

- `ghes_map()`（`drivers/acpi/apei/ghes.c:179`）用 `__set_fixmap()` 把错误记录物理页临时映射到固定虚拟地址，读完 `ghes_unmap()` 撤掉。
- `ghes_estatus_pool_init()`（`drivers/acpi/apei/ghes.c:199`）预先 `vmalloc` 一块内存做成 `gen_pool`，NMI 上下文里从这个无锁池分配节点，把错误记录拷出来，再甩给 irq_work 在普通上下文里慢慢处理。

```c
int ghes_estatus_pool_init(unsigned int num_ghes)
{
	ghes_estatus_pool = gen_pool_create(GHES_ESTATUS_POOL_MIN_ALLOC_ORDER, -1);
	if (!ghes_estatus_pool)
		return -ENOMEM;

	len = GHES_ESTATUS_CACHE_AVG_SIZE * GHES_ESTATUS_CACHE_ALLOCED_MAX;
	len += (num_ghes * GHES_ESOURCE_PREALLOC_MAX_SIZE);

	addr = (unsigned long)vmalloc(PAGE_ALIGN(len));
	...
	rc = gen_pool_add(ghes_estatus_pool, addr, PAGE_ALIGN(len), -1);
	...
}
```

### ghes_do_proc 分派

真正解析 CPER 记录的是 `ghes_do_proc()`（`drivers/acpi/apei/ghes.c:912`）。它遍历 estatus 里的每个 section，按 GUID 分派：

```c
	sev = ghes_severity(estatus->error_severity);
	apei_estatus_for_each_section(estatus, gdata) {
		sec_type = (guid_t *)gdata->section_type;
		sec_sev = ghes_severity(gdata->error_severity);
		...
		if (guid_equal(sec_type, &CPER_SEC_PLATFORM_MEM)) {
			atomic_notifier_call_chain(&ghes_report_chain, sev, mem_err);
			arch_apei_report_mem_error(sev, mem_err);
			queued = ghes_handle_memory_failure(gdata, sev, sync);
		} else if (guid_equal(sec_type, &CPER_SEC_PCIE)) {
			ghes_handle_aer(gdata);
		} else if (guid_equal(sec_type, &CPER_SEC_PROC_ARM)) {
			queued = ghes_handle_arm_hw_error(gdata, sev, sync);
		} else if (...CXL...) {
			...
		} else {
			ghes_defer_non_standard_event(gdata, sev);
			log_non_standard_event(sec_type, fru_id, fru_text,
					       sec_sev, err, gdata->error_data_length);
		}
	}

	if (sync && !queued) {
		dev_err(ghes->dev, ... "synchronous unrecoverable error (SIGBUS)\n", ...);
		force_sig(SIGBUS);
	}
```

ARM 处理器错误 section 由 `ghes_handle_arm_hw_error()`（`drivers/acpi/apei/ghes.c:554`）处理：先 `log_arm_hw_error()` 打 tracepoint，再遍历 `cper_arm_err_info` 数组，对"cache 错误且带物理地址"的条目调用 `ghes_do_memory_failure()`。只有 `sev` 与 `sec_sev` 都是 `GHES_SEV_RECOVERABLE` 时才尝试恢复，否则直接返回 false。

内存错误的恢复策略在 `ghes_handle_memory_failure()`（`drivers/acpi/apei/ghes.c:531`）：

```c
	if (sec_sev == GHES_SEV_CORRECTED &&
	    (gdata->flags & CPER_SEC_ERROR_THRESHOLD_EXCEEDED))
		flags = MF_SOFT_OFFLINE;
	if (sev == GHES_SEV_RECOVERABLE && sec_sev == GHES_SEV_RECOVERABLE)
		flags = sync ? MF_ACTION_REQUIRED : 0;

	if (flags != -1)
		return ghes_do_memory_failure(mem_err->physical_addr, flags);
```

即：CE 累计超阈值 → 软下线页面；可恢复 UC → 走 `memory_failure_queue()`，同步场景带 `MF_ACTION_REQUIRED` 让内核给当前进程发精确 SIGBUS。**本树 `CONFIG_MEMORY_FAILURE` 未启用**，这条路径即使 GHES 打开也不会真正隔离页面。

### 调用链

```
固件写 CPER 记录到 estatus 共享内存
  → SEA: do_sea → apei_claim_sea → ghes_notify_sea
  → NMI: ghes_notify_nmi
  → SDEI: ghes_sdei_normal_callback / ghes_sdei_critical_callback
  → ghes_in_nmi_queue_one_entry()      // fixmap 读 + gen_pool 拷贝
  → irq_work_queue(&ghes_proc_irq_work)
  → ghes_proc_in_irq() → ghes_do_proc()
      → ghes_handle_memory_failure() → memory_failure_queue()
      → ghes_handle_arm_hw_error()   → log_arm_hw_error() → trace_arm_event
      → ghes_handle_aer()            → PCIe AER
  → （同步且无人处理）force_sig(SIGBUS)
```

轮询/中断路径则简单得多：`ghes_proc()`（`drivers/acpi/apei/ghes.c:1176`）直接 `ghes_read_estatus()` → 若 `GHES_SEV_PANIC` 则 panic → 否则 `ghes_do_proc()` → `ghes_clear_estatus()`。

## KVM 侧 RAS

虚拟化场景下 RAS 的核心难题是：**guest 产生的 SError 不能在 host 上下文里爆出来**。KVM 的做法是在 guest→host 切换的最早时刻用 ESB 把错误"收"进 DISR_EL1，然后作为退出原因的一部分交给 host 处理。

hyp 向量每条入口的第一条指令就是 `esb`（`arch/arm64/kvm/hyp/hyp-entry.S:151`）：

```asm
.macro valid_vect target
	.align 7
661:
	esb
	stp	x0, x1, [sp, #-16]!
662:
	bti j
	b	\target

check_preamble_length 661b, 662b
.endm
```

`__kvm_hyp_vector` 中所有 `valid_vect` 槽位（el2_sync、el2_error、el1_sync/irq/fiq/error）都带这条 ESB；`invalid_vect` 用 nop 占位以保持 preamble 长度一致。

guest 退出时的收账逻辑在 `arch/arm64/kvm/hyp/entry.S:172`：

```asm
alternative_if ARM64_HAS_RAS_EXTN
	// If we have the RAS extensions we can consume a pending error
	// without an unmask-SError and isb. The ESB-instruction consumed any
	// pending guest error when we took the exception from the guest.
	mrs_s	x2, SYS_DISR_EL1
	str	x2, [x1, #(VCPU_FAULT_DISR - VCPU_CONTEXT)]
	cbz	x2, 1f
	msr_s	SYS_DISR_EL1, xzr
	orr	x0, x0, #(1<<ARM_EXIT_WITH_SERROR_BIT)
1:	ret
alternative_else
	dsb	sy		// Synchronize against in-flight ld/st
	isb			// Prevent an early read of side-effect free ISR
	mrs	x2, isr_el1
	tbnz	x2, #ISR_EL1_A_SHIFT, 2f
	ret
	nop
2:
alternative_endif
```

有 RAS 时：读 DISR → 存进 `vcpu->arch.fault.disr_el1`（`arch/arm64/include/asm/kvm_host.h:433`）→ 清 DISR → 在退出码上置 `ARM_EXIT_WITH_SERROR_BIT`。整个过程不需要 unmask SError，避免了在 host 上下文触发异常的风险。

没有 RAS 时只能走老办法：`dsb sy` + `isb` 后读 `ISR_EL1.A` 判断是否有 pending abort，若有则在 `abort_guest_exit_start`/`abort_guest_exit_end` 这个**单指令窗口**里 `msr daifclr, #4` 放开 SError，让它精确地在可控位置爆出来。

host 侧在 `handle_exit_early()`（`arch/arm64/kvm/handle_exit.c:490`）处理这个标志位：

```c
void handle_exit_early(struct kvm_vcpu *vcpu, int exception_index)
{
	if (ARM_SERROR_PENDING(exception_index)) {
		if (this_cpu_has_cap(ARM64_HAS_RAS_EXTN)) {
			u64 disr = kvm_vcpu_get_disr(vcpu);

			kvm_handle_guest_serror(vcpu, disr_to_esr(disr));
		} else {
			kvm_inject_serror(vcpu);
		}
		return;
	}

	exception_index = ARM_EXCEPTION_CODE(exception_index);
	if (exception_index == ARM_EXCEPTION_EL1_SERROR)
		kvm_handle_guest_serror(vcpu, kvm_vcpu_get_esr(vcpu));
}
```

注意它复用了 `disr_to_esr()` 和 `arm64_is_ras_serror()`——host 与 guest 共享同一套严重性语义。`kvm_handle_guest_serror()`（`arch/arm64/kvm/handle_exit.c:32`）：

```c
static void kvm_handle_guest_serror(struct kvm_vcpu *vcpu, u64 esr)
{
	if (!arm64_is_ras_serror(esr) || arm64_is_fatal_ras_serror(NULL, esr))
		kvm_inject_serror(vcpu);
}
```

与 `do_serror()` 结构完全一致，只是把"panic host"换成"向 guest 注入虚拟 SError"。`regs` 传 NULL 是因为此时没有 guest 的 pt_regs 现场。注入通过 `kvm_inject_serror_esr()`（`arch/arm64/kvm/inject_fault.c:360`）完成，它按 guest 当前是否屏蔽 SError 分两种做法：

```c
	if (!serror_is_masked(vcpu)) {
		pend_serror_exception(vcpu);
		esr |= FIELD_PREP(ESR_ELx_EC_MASK, ESR_ELx_EC_SERROR) | ESR_ELx_IL;
		vcpu_write_sys_reg(vcpu, esr, exception_esr_elx(vcpu));
		return 1;
	}

	vcpu_set_vsesr(vcpu, esr & ESR_ELx_ISS_MASK);
	*vcpu_hcr(vcpu) |= HCR_VSE;
	return 1;
```

未屏蔽时用软件模拟一次异常进入（因为硬件不会替我们填 ESR_ELx.EC）；已屏蔽时只写 `VSESR_EL2` 的 ISS 部分并置 `HCR_EL2.VSE`，等 guest 自己放开 A 位时由硬件投递。

guest 的 DISR 视图由 `VDISR_EL2` 提供，保存/恢复见 `arch/arm64/kvm/hyp/include/hyp/sysreg-sr.h:191` 与 `:334`；`arch/arm64/kvm/sys_regs.c:3474` 把 `SYS_DISR_EL1` 登记为可 trap 的系统寄存器，复位值 0。
